# Fast + Accurate AI Food Logging: Techniques Playbook (applied to STEADY failures)

*Research notes compiled 2026-11-11. All prices/model names are as fetched on 2026-11-11 unless stated. "Cited Findings" = evidence from the linked source; "Inferences" = our engineering opinion derived from that evidence, mapped to STEADY's known failures (unvalidated grams, unranked FTS limit 3, unbounded LLM per-100g estimates, INDB outliers, ~65% within tolerance / ~24% median kcal error, numbers too high + inconsistent).*

## 1. Food search/retrieval: hybrid search, ranking, aliases, multilingual; how vendors parse and match

### Takeaway
The fix for "same food → different rows" is to make retrieval a ranked, deterministic function: normalize + alias lookup first, then hybrid full-text (`ts_rank_cd`) + trigram + vector search fused with Reciprocal Rank Fusion (RRF) and a stable tie-break, and only then let an LLM choose among top-k candidates (never invent nutrients). Every commercial NL nutrition API (Nutritionix, Edamam, FatSecret, Passio) follows the same shape: parse text → ranked candidates from a curated DB → named household measures with gram weights.

### Cited Findings
**Postgres / Supabase mechanics**
- Supabase's reference hybrid search runs a full-text CTE (`fts @@ websearch_to_tsquery(query_text)` ranked by `ts_rank_cd`) and a semantic CTE (`row_number() over (order by embedding <#> query_embedding)`), then full-outer-joins them and orders by `coalesce(1.0/(rrf_k + full_text.rank_ix),0)*full_text_weight + coalesce(1.0/(rrf_k + semantic.rank_ix),0)*semantic_weight`; defaults `full_text_weight=1`, `semantic_weight=1`, `rrf_k=50`; each CTE fetches `least(match_count,30)*2` rows; GIN index on the tsvector, HNSW (`vector_ip_ops`) on the embedding; query embedding must come from the same model/dimensions as the column — [Supabase: Hybrid search](https://supabase.com/docs/guides/ai/hybrid-search)
- Supabase notes `ts_rank_cd` is "not indexable" but only ranks rows already matched by the `where` clause, so cost stays bounded; its example tsvector is generated with the `'english'` config — [Supabase: Hybrid search](https://supabase.com/docs/guides/ai/hybrid-search)
- pg_trgm: `similarity()` (0–1), `word_similarity()` (best match of query against any contiguous extent of the target — good for "paneer" inside "paneer butter masala"), `strict_word_similarity()` (word-boundary aligned); operators `%`, `<%`, `<<%`, distance `<->`, `<<->`, `<<<->`; default thresholds `similarity_threshold=0.3`, `word_similarity_threshold=0.6`, `strict_word_similarity_threshold=0.5` — [PostgreSQL docs: pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html)
- pg_trgm index support: GIN (`gin_trgm_ops`) supports similarity filtering but **not** distance ordering; GiST (`gist_trgm_ops`) additionally supports KNN `ORDER BY t <-> 'query' LIMIT n`; non-alphanumeric characters are ignored; comparisons case-insensitive "in a default build"; the docs do not document multibyte/non-ASCII behavior — [PostgreSQL docs: pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html)

**How vendors parse and match**
- Nutritionix `POST /v2/natural/nutrients` takes a free-text `query` ("1 cup flour, 1 pinch of salt…"); each returned food carries `serving_weight_grams`, an `alt_measures` array (`measure`, `qty`, `serving_weight` in g) and `tags` (`item`, `measure`, `quantity`, `food_group`); documented scaling is `(alt serving_weight ÷ serving_weight_grams) × full_nutrients`; flags include `use_raw_foods`, `use_branded_foods`, `line_delimited`, `num_servings`. Matching/NLP internals and the default-serving rule are not documented (the "grape" example silently returns 10 grapes = 49 g) — [Nutritionix NL nutrients docs (Syndigo)](https://docx.syndigo.com/developers/docs/natural-language-for-nutrients)
- Edamam parser returns `parsed` (top match plus the quantity and measure extracted from the query, e.g., "1 whole chicken" → qty 1, measure "whole") and `hints` (all matching foods ordered by relevance, each with every available measure); measures are ontology URIs (`…edamam.owl#Measure_cup`), and **qualifiers** such as "large"/"small" change a measure's gram weight; results can be restricted by `category` (`generic-foods`, `packaged-foods`, `generic-meals`, `fast-foods`) — [Edamam Food Database API docs](https://developer.edamam.com/food-database-api-docs)
- FatSecret NLP endpoint `https://platform.fatsecret.com/rest/natural-language-processing/v1` "breaks down natural language and returns a list of foods from the fatsecret database," optional `include_food_data`; marketed as detecting food items, portions and nutrition "mapped to a given country-specific dataset," NLP in 24 languages; sold as an optional add-on, not in the base tier — [FatSecret NLP docs](https://platform.fatsecret.com/docs/v1/natural.language.processing); [FatSecret features page](https://platform.fatsecret.com/features/image-recognition-and-nlp); [FatSecret editions](https://platform.fatsecret.com/api-editions)
- Passio Nutrition-AI: SDK + REST; cloud recognition returns all foods in an image, with `nutritionPreview` "pre-calculated from Passio's nutrition database"; claims a 2.5M+ food database; usage metered in "tokens" (vendor claims) — [Passio AI docs summary](https://passio.gitbook.io/nutrition-ai/fundamentals/ai-docs-summary); [Passio platform](https://www.passio.ai/platform); [Passio cost breakdown](https://www.passio.ai/cost-breakdown)
- FAO/INFOODS publishes formal "Guidelines for Food Matching" (matching consumed foods to food-composition entries) as one of three companion guidelines (matching; checking data before publication; converting units/denominators) — [FAO INFOODS standards & guidelines](https://www.fao.org/infoods/infoods/standards-guidelines/en/); [INFOODS Guidelines for Food Matching v1.2 (PDF)](https://www.fao.org/fileadmin/templates/food_composition/documents/Nutrition_assessment/INFOODSGuidelinesforFoodMatching_version_1_2.pdf)

**Embeddings (cost side)**
- text-embedding-3-small $0.02 / 1M tokens, text-embedding-3-large $0.13 — [OpenAI pricing](https://developers.openai.com/api/docs/pricing); gemini-embedding-001 $0.15, gemini-embedding-2 $0.20 per 1M text tokens — [Gemini API pricing](https://aistudio.google.com/docs/pricing)

### Inferences
- **Root cause of STEADY's inconsistency**: `websearch_to_tsquery … LIMIT 3` with no `ORDER BY` returns rows in physical/plan order, which can change with vacuum, index choice or new inserts — so identical text can legitimately yield different rows. Any fix must end in `ORDER BY score DESC, source_priority ASC, food_id ASC` (a total order) so ties are broken the same way every time.
- **Recommended retrieval cascade (single Postgres RPC, one round trip per meal):** (1) normalize (lowercase, `unaccent`, strip quantities, singularize) → (2) exact hit on a `food_alias(alias_norm, food_id, lang, script, source)` table (roti = chapati = phulka = fulka = "रोटी"; dal = daal = dhal) → (3) if no exact hit, fuse FTS (`ts_rank_cd`, using the `'simple'` text-search config for non-English/romanized names because the `'english'` stemmer mangles Hindi transliterations), trigram `word_similarity` (catches spelling variants like "paneer/panir"), and pgvector cosine (catches cross-lingual/semantic matches like "egg curry" ↔ "anda curry") via RRF → (4) return top ~8 candidates with scores to the LLM, which returns a `food_id` from an enum/strict schema or "none".
- Aliases should be the primary multilingual mechanism (cheap, deterministic, auditable); embeddings are the long-tail fallback. Embedding cost is negligible at STEADY scale (a 10-token query × 300 logs/month ≈ 3K tokens ≈ $0.00006/user/month on text-embedding-3-small), so the decision is about quality/latency, not price.
- Promote verified rows: add `source_priority` (verified curated base > IFCT > USDA Foundation/SR Legacy > FNDDS > INDB recipe-computed > AI estimate) to the ORDER BY so a lower-quality row cannot outrank a curated one on a near-tie.
- Vendor pattern worth copying: every vendor returns **named measures with gram weights per food** (Nutritionix `alt_measures`, Edamam measures + qualifiers). STEADY should store `food_portion(food_id, unit, qualifier, grams, source)` rather than letting the LLM output grams.

### Gaps
- No vendor publishes its matching/ranking algorithm (Nutritionix, FatSecret, Passio internals are undocumented); claims about accuracy are marketing.
- Could not retrieve OpenAI's MIRACL/MTEB multilingual scores for text-embedding-3 (page returned 403); no food-name-specific benchmark of multilingual embedding models (Hindi/Tamil/romanized) was found.
- No published evaluation of hybrid FTS+trigram+vector search specifically for food-name matching; RRF k=50 and equal weights are Supabase defaults, not tuned for food — must be tuned on STEADY's eval set.
- pg_trgm behavior on Devanagari/Tamil script is undocumented; needs testing against the DB's locale.

## 2. Portion estimation: household measures, Indian portions, per-user learning, clarifying questions, photo volume

### Takeaway
Portion (grams) is the dominant error source in published studies, and LLMs do worse with natural household units than with grams. The robust pattern is: LLM extracts `{count, unit, size qualifier}` only; code converts to grams from a portion table (FNDDS/NIN/INDB + STEADY's own curated table), overridden by the user's own learned history. Free-text follow-up questions have *not* been shown to improve accuracy and add friction; one-tap size chips are the better bet. Photo depth/LiDAR gets ~12–15% error in controlled studies, not ±10% in the wild.

### Cited Findings
**Standard portion tables**
- USDA FNDDS ships a Food Portions & Weights component (FoodWeights + FoodPortionDesc files, plus subcode files); the 2021–2023 release contains gram weights for 22,046 portions — [FNDDS 2021–2023 factsheet](https://ars.usda.gov/ARSUserFiles/80400530/pdf/fndds/FNDDS_2021_2023_factsheet.pdf); [FNDDS 2021–2023 documentation](https://ars.usda.gov/ARSUserFiles/80400530/pdf/fndds/2021_2023_FNDDS_Doc.pdf)
- FoodData Central's data dictionary defines `gram_weight` and household serving text (amount + unit in household units) for portions — [FDC data dictionary](https://fdc.nal.usda.gov/portal-data/external/dataDictionary)
- ICMR-NIN Dietary Guidelines for Indians (2024) includes "Annexure II: Raw food item measures using household utensils" (verified only via table of contents; values not extracted) — [ICMR-NIN DGI 2024 (PDF)](https://www.nin.res.in/dietaryguidelines/pdfjs/locale/DGI24thJune2024fin.pdf)
- Secondary/unverified: a commercial blog attributes to NIN a katori set of big 360 ml, medium 200 ml, small 155 ml and 115 ml, and quotes NIN that "substantial variances in home measures such as measuring cups, spoons, or katoris" complicate intake data — [Instacuppa ladle guide (secondary)](https://instacuppastore.com/blogs/main-page/ladle-size-guide-how-much-dal-one-karchhi-pours-and-why-yours-dribbles)
- Roti weight is not consistent across secondary sources: "1 serving = 30 g (1 roti)" — [Netmeds](https://www.netmeds.com/health-library/post/what-is-portion-size-what-is-the-difference-between-portion-vs-serving-size-tips-to-measure); "a peda of roti is 50 g" — [OdishaBytes](https://odishabytes.com/?p=260820) (both non-authoritative)
- A 2016 Indian Journal of Community Medicine study standardized reference portion sizes for a rural North Indian FFQ using household utensil surveys (method precedent for building local portion tables) — [IJCM 2016 (DOAJ)](https://doaj.org/article/2b9bde2cd1cc4ad4860d3aa057281cbb)
- INDB (Vijayakumar et al., Curr Dev Nutr 2024): 1,014 recipes (611 + 513 from two University of Delhi manuals + 148 from food blogs), each with ingredient amounts, total recipe weight, number of servings and serving size; nutrients computed per 100 g and per serving; serving sizes missing for pickles/preserves and weaning foods; only 42.62% of recipe ingredients matched a nutrient-retention factor; code on GitHub — [INDB paper (PMC)](https://pmc.ncbi.nlm.nih.gov/articles/PMC11277795/); [INDB GitHub](https://github.com/lindsayjaacks/Indian-Nutrient-Databank-INDB)

**LLMs and natural units**
- NutriBench pairs 5,532 meal descriptions in natural servings with the same meals in metric (gram) servings; "most models exhibit higher MAE when using natural serving measures" (GPT family the exception, performing better with metric) — [NutriBench v6](https://arxiv.org/html/2407.12843v6)

**Clarifying questions vs defaults**
- SnappyMeal (Univ. of Washington, Nov 2025; Gemini 2.5 Flash app, Nutrition5k technical eval on 100 images): calorie MAE 148.88 kcal without vs 161.82 kcal **with** follow-up questions; carb MAE 15.30 → 18.00 g; fat 8.05 → 9.58 g; authors found "no conclusive evidence that the follow-up questions directly improved nutrition estimation"; 34.3% of follow-ups concerned quantity/portion; in a 3-week deployment (6 completers, 502 logs) users found questions not context-adapted, wanted to skip them for simple foods (e.g., banana); 20.7% of logs were edited and 5.8% deleted — [SnappyMeal arXiv 2511.03907](https://arxiv.org/html/2511.03907v1)
- Diabot-GPT-4o (validated against weighed food records): common errors included inaccurate portion-size estimates and obscured food in images — [Diabot GPT-4o (UMN)](https://experts.umn.edu/en/publications/customized-multimodal-diabot-gpt-4o-enhances-accuracy-of-image-ba/)

**Photo-based volume estimation**
- Depth-sensing smartphone app (JMIR mHealth 2020, preclinical): mean relative absolute error 14.0% for meal weight (35.1 g absolute) and ~12.7% for energy; worse for cooked meals than for breakfasts/snacks — [JMIR mHealth 2020;8(3):e15294](https://mhealth.jmir.org/2020/3/e15294/PDF)
- 2026 review: mobile LiDAR spatial resolution "often insufficient for dietary assessment"; small granular foods (rice grains, nuts) are smoothed over, causing significant volume errors — [Food Portion Estimation: From Pixels to Calories (arXiv 2602.05078)](https://arxiv.org/html/2602.05078v1)
- Monocular camera + 3D object scaling (2024): 31.10 kcal (17.67%) average error on its own dataset — [arXiv 2404.12257](https://arxiv.org/html/2404.12257v2)
- Nutrition5k (Google, CVPR 2021): ~5k real dishes with component weights and depth images; secondary summary reports calorie MAE 26.1% (2D direct), 18.8% (RGB-D), 16.5% (two-stage portion-then-density) — primary numbers not verified — [Nutrition5k arXiv 2103.03375](https://arxiv.org/abs/2103.03375); [secondary review](https://liner.com/review/nutrition5k-towards-automatic-nutritional-understanding-generic-food)
- DPF-Nutrition (monocular predicted depth, on Nutrition5k): PMAE 14.7% kcal, 10.6% mass, 20.2% protein, 22.6% fat, 20.7% carbs — [DPF-Nutrition (MDPI Foods 2023)](https://mdpi.com/2304-8158/12/23/4293)

**Real-world app bias**
- NUTRITION 2026 (ASN) abstract, as reported: four popular AI photo-logging apps tested against meals weighed to 0.1 g missed about a third of plate energy (underestimation) — [Epocrates report (403 on fetch; search snippet)](https://www.epocrates.com/online/article/ai-calorie-counting-apps-miss-a-third-of-meal-calories); an earlier 102-meal study found four AI apps underestimated meals by 250–345 kcal on average (secondary) — [PCTechMag summary (secondary)](https://pctechmag.com/?p=99702)

### Inferences
- **Stop letting gpt-4o-mini guess grams.** Have the LLM emit `{food, count, unit ∈ enum[piece, katori, bowl, cup, plate, tbsp, tsp, glass, slice, g, ml], size ∈ enum[small, medium, large, null]}`; code resolves grams via `food_portion(food_id, unit, size)` → category default → global unit default. This makes grams deterministic and fixable in data rather than prompts.
- **Per-user portion learning (simple, robust):** store every user edit as `(user_id, food_id, unit) → grams`; use the median of the last ~5 confirmed values once ≥2 exist (median resists one-off typos); otherwise fall back to the table. This turns the 20.7%-style edit rate into training signal and directly attacks "numbers too high" for users with smaller rotis/katoris.
- **Clarify only when it matters:** given SnappyMeal's result, avoid free-text follow-ups. Instead show the default with one-tap size chips (S/M/L with grams visible) only when (a) portion uncertainty is high and (b) the item is calorie-dense (e.g., > 150 kcal at default) — a kcal-weighted trigger keeps friction low.
- STEADY's current hint table (roti 40 g, katori 150 g, plate 200 g) has no single authoritative source; the NIN Annexure II, INDB per-serving sizes and FNDDS portions should be loaded as data and reconciled, with region overrides (North vs South Indian roti/dosa sizes differ — unverified, needs data).
- Photo portions: treat photo grams as a prior with explicit uncertainty; depth sensing (~12–15% in lab) is not available on most Android devices and doesn't reach ±10% for mixed/granular Indian dishes, so for photos the realistic target is "consistent and unbiased," not ±10%.

### Gaps
- Could not extract authoritative gram weights for roti/chapati, katori-of-dal, plate-of-rice from ICMR-NIN (PDF too large to parse in this session); secondary sources conflict (30 g vs 50 g roti).
- No published study on per-user portion learning in calorie apps was found (approach above is engineering opinion).
- No controlled study comparing one-tap size chips vs free-text clarifying questions vs silent defaults on weighed-meal accuracy.
- Nutrition5k primary result numbers not verified (PDF text extraction unavailable).

## 3. Consistency/determinism: caching, temperature, structured outputs, seeds, self-consistency, calibration

### Takeaway
You cannot buy determinism from the model API: temperature-0 outputs vary with server batch composition, OpenAI's `seed` is "mostly" reproducible, and Anthropic's current API (2026-10-21) rejects `temperature` entirely. Consistency must be architectural: cache by normalized input, constrain the LLM to small enum/schema outputs, and make every number come from a deterministic DB + portion lookup so the LLM only affects *which* food, not *how many calories*.

### Cited Findings
- Thinking Machines Lab: temperature-0 nondeterminism is caused mainly by lack of **batch invariance** (kernel results depend on batch size, which depends on server load), not just floating-point concurrency; Qwen3-235B at temp 0, 1,000 samples of the same prompt → 80 unique completions (identical for the first 102 tokens); with batch-invariant kernels all 1,000 were identical, at a throughput cost (Qwen3-8B, 1,000 sequences: 26 s default → 55 s unoptimized deterministic → 42 s with improved attention) — [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- OpenAI `seed`: if seed, request parameters and `system_fingerprint` all match, outputs "will mostly be identical," but determinism is not guaranteed; the fingerprint changes when OpenAI updates infrastructure numerics (archived cookbook) — [OpenAI cookbook: Deterministic outputs with seed (archive)](https://git.blob42.xyz/Archives/openai-cookbook/blame/commit/90c6ce1e545c416af681010220493272e0f0f462/examples/Deterministic_outputs_with_the_seed_parameter.ipynb)
- OpenAI Structured Outputs with `strict: true` scored 100% schema adherence in OpenAI's eval (gpt-4o-2024-08-06) — this guarantees the JSON *shape*, not identical content — [OpenAI: Introducing Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/)
- Anthropic API version `2026-10-21`: any Messages request sending `temperature`, `top_p` or `top_k` returns HTTP 400 on every model (even default values); Claude 4.7+ models already accepted only default sampling; there is "no replacement setting" for a call that lowered temperature for consistency. Structured outputs via `output_config.format` and `strict: true` tools are supported — [Anthropic API migration 2026-10-21](https://platform.claude.com/docs/en/api/migration-2026-10-21) (as summarized in Anthropic's claude-api reference, cached 2026-11-03); [Anthropic structured outputs docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Repeatability has been measured in nutrition studies: Hoang et al. (JAMA Netw Open 2024) queried ChatGPT-3.5/4 five times per food and used coefficient of variation; energy was within 10% for ~35–48% of 222 foods with CV < 10% (secondary reports) — [HealthDay summary](https://www.healthday.com/healthpro-news/health-technology/chatgpt-provides-accurate-nutritional-information); [Drugs.com summary](https://www.drugs.com/news/chatgpt-provides-accurate-nutritional-116782.html)
- A 2025 Nutrients study of five AI chatbots vs four dietitians (dietitians used measured food weights) reported calorie-estimate coefficients of variation of 20%–70% (search-snippet level; full text not retrieved) — [Nutrients 2025, 17(19):3044](https://www.mdpi.com/2072-6643/17/19/3044)
- Chain-of-thought improved average accuracy across 12 models on NutriBench from 43.24% to 47.46% and answer rate from 95.59% to 97.14% — [NutriBench v6](https://arxiv.org/html/2407.12843v6)

### Inferences
- **Cache layer (per user, then shared):** key = `sha256(parser_version | locale | normalize(text))`; value = the resolved `[food_id, unit, size, grams]` list (not the kcal — kcal is recomputed from the current DB so data fixes propagate). Per-user cache first (captures their portions/corrections), then a shared cache only for entries that hit verified foods. Bump `parser_version` whenever the prompt/model changes to invalidate safely. This replaces the "global forever" cache that froze bad matches.
- **Shrink the LLM's degrees of freedom:** the LLM should output only categorical fields (food string or candidate `food_id` from a provided list, unit enum, size enum, count). Categorical outputs are far more stable across runs than free numeric outputs; any residual wording drift is absorbed by alias normalization before lookup.
- **Never let the LLM emit kcal/macros on the hot path**; if no DB match exists, an LLM per-100g estimate must be stored once as a new "AI estimate" row (with validation, §4) and reused thereafter, so the same unknown food gets the same number every time.
- **Self-consistency only when cheap and needed:** for low-confidence items (retrieval top-1 vs top-2 RRF score margin below a threshold, or LLM returned "none"), run 3 parallel samples and majority-vote the `food_id`; parallel calls add cost, not much latency.
- **Confidence should come from retrieval geometry, not LLM self-report:** use alias exact-hit = high; RRF margin and trigram similarity as features; surface low-confidence items in UI ("tap to confirm") rather than silently logging.
- **For STEADY's Claude nutritionist (claude-sonnet-4-6):** upgrading the Anthropic SDK to a release that sends `2026-10-21` will 400 any call still passing `temperature` — check before upgrading.

### Gaps
- No published measurement of run-to-run variance for OpenAI/Gemini/Claude structured outputs specifically on food parsing; STEADY must measure it (see §6).
- Whether OpenAI's `seed` is still honored on the newest (gpt-5.x / gpt-6-luna) models was not confirmed from current official docs.
- Literature on calibration of LLM verbalized confidence for nutrition was not found in this session.

## 4. Validation layers: Atwater, plausible ranges, outlier detection, raw vs cooked yields

### Takeaway
Cheap deterministic checks catch most bad rows and bad AI estimates: Atwater energy reconciliation (4/4/9/7 kcal/g), mass-balance (macros ≤ 100 g per 100 g), a hard 900 kcal/100 g ceiling, category-percentile ranges, and cross-source robust outlier tests. Raw-vs-cooked state must be explicit because yield factors change kcal/100 g by large factors.

### Cited Findings
- Atwater general factors: protein 4 kcal/g (17 kJ/g), carbohydrate 4 kcal/g, fat 9 kcal/g (37 kJ/g); alcohol 7 kcal/g; dietary fibre commonly 2 kcal/g (8 kJ/g); extended general system adds organic acids 3 kcal/g and polyols 2.4 kcal/g — [FAO Food & Nutrition Paper 77 (2003), ch.3](https://www.fao.org/3/Y5022E/y5022e04.htm); [FAO component conventions presentation](https://www.fao.org/fileadmin/templates/food_composition/documents/Presentations/Food_Composition_-_Component_conventions_and_expressions.pdf)
- FAO notes energy factor systems assume fixed per-component factors and that combinations of analytical methods and factors give "myriad possibilities for expressing the energy content" — i.e., sources legitimately differ by a few percent — [FAO Food energy abstract](https://fao.org/fileadmin/templates/food_composition/documents/book_abstracts/Food_energy.pdf); [FAO FNP 77 index](https://www.fao.org/3/Y5022E/Y5022E00.htm)
- INFOODS food-matching guidance: energy values should not be copied on their own; macronutrients are needed to calculate energy, using FAO (2003) conversion factors — [INFOODS Guidelines for Food Matching](https://www.fao.org/fileadmin/templates/food_composition/documents/upload/INFOODSGuidelinesforFoodMatching_final_july2011.pdf)
- FAO/INFOODS "Guidelines for Checking Food Composition Data prior to Publication of a User Table/Database" (v1.0, 2012) lays out internal checks on values and documentation before data enters a database — [B4FN listing of the guidelines](https://b4fn.org/resources/publications/publication-item/faoinfoods-guidelines-guidelines-for-checking-food-composition-data-prior-to-the-publication-of-a); [FAO INFOODS standards](https://www.fao.org/infoods/infoods/standards-guidelines/en/)
- USDA Table of Cooking Yields for Meat and Poultry (Release 2): cooking yield %, moisture change and fat change per cut and cooking method; USDA's Nutrient Data Lab applies cooking yields and/or nutrient retention factors to convert raw ingredient values into cooked-food values — [USDA Cooking Yields PDF](https://ars.usda.gov/ARSUserFiles/80400535/Data/retn/USDA_CookingYields_MeatPoultry02.pdf); [Ag Data Commons dataset](https://agdatacommons.nal.usda.gov/articles/dataset/USDA_Table_of_Cooking_Yields_for_Meat_and_Poultry/24660864/1); [SR11 documentation](https://www.ars.usda.gov/ARSUserFiles/80400525/data/sr11/sr11_doc.pdf)
- INDB matched retention factors for only 42.62% of recipe ingredients — so many INDB recipe values are computed without full cooking-loss/retention adjustment — [INDB paper (PMC)](https://pmc.ncbi.nlm.nih.gov/articles/PMC11277795/)

### Inferences
- **Hard physical bound:** pure fat is 9 kcal/g, so no food can exceed ~900 kcal/100 g. INDB's kachori at 713 kcal/100 g would require ~79 g fat per 100 g if it were all fat — implausible for a fried pastry with a flour/dal filling; such a row should be auto-quarantined.
- **Validation rules to run on every DB row at import and on every AI estimate before use:**
  1. Atwater residual: `|kcal − (4P + 4C + 9F + 7·alcohol [+2·fibre if C is total carb by difference])| / kcal`; flag > 15–20% (tolerance is our opinion; FAO notes legitimate method differences).
  2. Mass balance: `P + C + F (+ fibre + water + ash if present) ≤ ~102 g per 100 g`.
  3. Hard ceiling kcal ≤ 900/100 g; floor ≥ 0; water-like foods near 0.
  4. Category range: compute p1–p99 kcal/100 g per FNDDS/IFCT category from the data itself (data-derived, not hand-picked), flag outside.
  5. Cross-source robust outlier: for each canonical food with ≥ 3 sources (INDB, IFCT, USDA, curated), compute median and MAD; flag |x − median| > 3·MAD (robust z > 3).
  6. State check: a `state ∈ {raw, cooked, as_prepared}` column; reject matching a "cooked" log to a "raw" row (e.g., raw rice ~350 kcal/100 g vs cooked ~130 kcal/100 g is the classic 2.5–3× error — values are common knowledge, verify against FDC).
- **AI per-100g estimates**: require the model to output macros (P/C/F) and *derive* kcal by Atwater in code (per INFOODS advice) rather than trusting a model-stated kcal; clamp to the category range; persist with `source='ai_estimate'`, lowest `source_priority`, and queue for human review.
- Flagged rows should be demoted in ranking (§1 `source_priority`) rather than deleted, so an audit trail remains.

### Gaps
- Could not retrieve the exact numeric tolerances in the INFOODS checking guidelines (e.g., acceptable energy-recalculation difference, sum-of-proximates window); the 15–20% and ~102 g thresholds above are our proposal.
- No published per-category kcal/100 g plausibility table for Indian foods was found; must be computed from IFCT/INDB/FNDDS.
- USDA nutrient retention factor table itself was not retrieved (only cooking-yield table).

## 5. Speed: single call vs agents, streaming, parallel DB lookups, caching, edge latency, STT

### Takeaway
Hitting "ring updates ~2.5 s after speaking" is a budgeting exercise: streaming STT finalization (~0.15–0.5 s after end of speech) + one short structured LLM call with thinking off (dominant cost is output tokens) + one batched DB RPC + optimistic UI. Agent loops and multiple sequential LLM calls are the main latency risk; caches that skip the LLM entirely are the biggest win.

### Cited Findings
- OpenAI latency guide principles: (1) process tokens faster (smaller models); (2) generate fewer tokens — "cutting 50% of your output tokens may cut ~50% of your latency," including shorter JSON field names; (3) fewer input tokens matters less — halving the prompt improves latency only ~1–5%; put dynamic content late to maximize the cacheable prefix; (4) make fewer requests — merge sequential steps into one prompt with one structured response; (5) parallelize independent steps, use speculative execution for likely outcomes; (6) make users wait less — streaming is most effective, plus chunking/progress states; (7) don't default to an LLM — use caching, hash maps, precomputed responses — [OpenAI latency optimization guide](https://developers.openai.com/api/docs/guides/latency-optimization)
- Claude Haiku 5.5 runs adaptive thinking by default (default effort `medium`); thinking can be disabled only at effort `high` or below; thinking tokens are billed and delay the first visible output — [Anthropic models overview](https://platform.claude.com/docs/en/about-claude/models/overview) (per Anthropic claude-api reference, cached 2026-11-03)
- Gemini paid pricing states output prices "including thinking tokens" for Flash tiers — [Gemini API pricing](https://aistudio.google.com/docs/pricing)
- STT streaming (mostly vendor-reported): AssemblyAI Universal-3 Pro Streaming P50 ≈ 150 ms / P90 ≈ 240 ms after VAD endpoint (Mar 2026) — [AssemblyAI streaming benchmarks](https://www.assemblyai.com/docs/streaming/benchmarks); Coval's comparison ranks Deepgram Flux fastest, Nova-3 ~0.46 s slower at P50, AssemblyAI ~761 ms slower than Deepgram at P50; Deepgram Flux Multilingual launched 2026-04-29 — [Coval STT benchmarks 2026](https://www.coval.dev/blog/best-speech-to-text-providers-in-2026-independent-benchmarks-and-how-to-choose); vendor-run FLEURS test: time-to-first-transcript 295 ms (Smallest.ai), 310 ms (Deepgram), 480 ms (gpt-4o-mini-transcribe) — [Smallest.ai benchmark (vendor)](https://smallest.ai/blog/comparative-analysis-of-streaming-asr-systems-a-technical-benchmark-study)
- OpenAI transcription pricing: gpt-4o-transcribe $0.006/min, gpt-4o-mini-transcribe $0.003/min, gpt-realtime-whisper (streaming) $0.017/min — [OpenAI pricing](https://developers.openai.com/api/docs/pricing); one comparison lists gpt-4o-transcribe as not real-time-streaming, and GPT-Realtime-Whisper (released 2026-05-07) as the low-latency streaming option — [Coval STT benchmarks 2026](https://www.coval.dev/blog/best-speech-to-text-providers-in-2026-independent-benchmarks-and-how-to-choose)
- Claude prompt caching: cache hits on Haiku 5.5 cost $0.01/MTok vs $0.10 base; minimum cacheable prefix 286 tokens for Haiku 5.5 — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- LLM speed leaderboards for Nov 2026 found via search were mutually inconsistent and some implausible; Artificial Analysis is the reference source but its tables were not retrieved — [Artificial Analysis leaderboard](https://artificialanalysis.ai/leaderboards/models)

### Inferences
- **Latency budget for voice → ring (target ≤ 2.5 s after end of speech):** STT final ~0.2–0.5 s (streaming; start the socket when the mic opens) → per-user cache check ~20–50 ms (skip LLM on hit) → single LLM parse call with thinking off, ~80–150 output tokens of compact JSON, ~0.6–1.2 s typical for a small model (unverified; measure p50/p90) → one Postgres RPC that takes the whole item array and does alias/FTS/trigram/vector retrieval for all items in one round trip (~50–150 ms with proper indexes) → render. Leaves ~0.5 s headroom.
- **Avoid the current multi-hop path on the hot path:** USDA FDC API calls (3 tiers) and a second "LLM picks candidate" call are sequential network hops. Move USDA/FNDDS data into Postgres (bulk import) so lookups are local; if an LLM pick is needed, fold candidate retrieval *before* the single LLM call (retrieve candidates from the raw transcript by n-grams/aliases, include top-k in the prompt) so there is one LLM call total.
- **Speculative/optimistic UI:** as soon as STT partials stabilize, show parsed food chips; update the ring with cached per-user values immediately and reconcile when the server returns. Users perceive the first visible change, not the final number (OpenAI guide principle 6).
- **Edge placement:** run the Supabase Edge Function in the same region as the database; one Edge → DB RPC rather than multiple supabase-js queries.
- **Prompt hygiene:** keep the system prompt + examples static (cacheable prefix ≥ 286 tokens for Haiku 5.5 caching; OpenAI caches automatically for long prefixes), put the transcript last.
- Thinking/reasoning modes should be off for the parse route; reserve reasoning for the nutritionist chat.

### Gaps
- No trustworthy, dated (Nov 2026) TTFT/throughput numbers for gpt-6-luna, gpt-5.4-nano/mini, Claude Haiku 5.5 or Gemini 3.x Flash-Lite were retrieved; STEADY should measure p50/p90 from its Edge Function region.
- STT latency numbers are largely vendor-published, with inconsistent definitions (first partial vs final after VAD); Hindi/Hinglish code-switching accuracy was not found in these benchmarks.
- Supabase Edge Function cold-start latency figures were not researched in this session.

## 6. Evaluation: trustworthy eval sets, NutriBench, Nutrition5k, signed bias, per-category error, consistency testing

### Takeaway
A trustworthy eval needs weighed/recipe-computed ground truth independent of the system under test, reports **signed bias** (STEADY's "too high" complaint) separately from absolute error, breaks error down by category, cuisine and input mode, and adds a repeat-run consistency test. Oracle ablations (give true food / true grams) separate identification, portion and composition error so fixes target the biggest bucket.

### Cited Findings
- NutriBench construction: real intake records from WWEIA (nutrients from FNDDS) and FAO/WHO GIFT across 11 countries (incl. India and Sri Lanka) turned into 11,857 natural-language meal descriptions by GPT-4o-mini, then **human-verified** by an author for omissions/inaccuracies; reports Acc@7.5 g carbs, MAE and answer rate; per-country MAE for GPT-4o+CoT ranged from 2.20 g (Nigeria) to 15.12 g (Sri Lanka) — [NutriBench v6](https://arxiv.org/html/2407.12843v6); [ICLR 2025 poster](https://iclr.cc/virtual/2025/poster/30896)
- Nutrition5k: ~5k real cafeteria dishes with component weights, depth images and "high accuracy nutritional content annotation"; authors claim their model outperforms professional nutritionists — [Nutrition5k arXiv](https://arxiv.org/abs/2103.03375)
- Weighed-meal validation precedents: NUTRITION 2026 test of four apps against meals weighed to 0.1 g (≈ one-third energy underestimation) — [Epocrates report](https://www.epocrates.com/online/article/ai-calorie-counting-apps-miss-a-third-of-meal-calories); Diabot-GPT-4o validated against weighed food records — [UMN Experts](https://experts.umn.edu/en/publications/customized-multimodal-diabot-gpt-4o-enhances-accuracy-of-image-ba/); depth app vs weighed meals reported relative absolute error with SD — [JMIR mHealth 2020](https://mhealth.jmir.org/2020/3/e15294/PDF)
- O'Hara et al. (Nutrients 2025, 17(4):607): ChatGPT on 114 meal photos vs dietitians; ICC 0.31–0.67; >10% difference for 13 nutrients, underestimating 11; poor agreement for 10/16 nutrients — [Nutrients 2025;17(4):607](https://mdpi.com/2072-6643/17/4/607)
- Repeat-query consistency methodology (five repeats per item, coefficient of variation) used by Hoang et al. 2024 — [HealthDay summary](https://www.healthday.com/healthpro-news/health-technology/chatgpt-provides-accurate-nutritional-information)
- In-the-wild proxy metrics: SnappyMeal logged edit rate (20.7%) and delete rate (5.8%) of 502 logs — [SnappyMeal arXiv](https://arxiv.org/html/2511.03907v1)
- A Nov 2025 Nutrients study (195 dishes incl. home-prepared weighed meals) reports GPT-5 accuracy improved significantly when ingredient and preparation context was supplied (snippet only; fetch blocked) — [Nutrients 2025, 17(22):3613](https://www.mdpi.com/2072-6643/17/22/3613)

### Inferences
- **Metrics to report on every run:** signed mean % error (bias; directly measures "too high"), median absolute % error, % items within ±10% and ±20%, the same at **meal** and **day** level (item errors partially cancel at day level, which is what the ring shows), per category (grains/breads, dals/curries, fried snacks, beverages, sweets, packaged), per cuisine/locale, per input mode (text/voice/photo).
- **Consistency test:** run each eval input N = 5 times (and once a day over a week to catch provider drift); report % of inputs with identical `food_id`s and identical kcal, and kcal CV. Target ~100% identical on cache-miss paths after §3 changes.
- **Oracle ablations** (cheap and very diagnostic): (a) give the true food_id → measures portion + composition error; (b) give true grams → measures matching + composition error; (c) give both → pure database error (catches INDB outliers). Whichever bucket is biggest gets fixed first.
- **Ground truth sources ranked:** weighed home meals computed from IFCT/INDB per-ingredient recipes (best, India-specific) > FNDDS-coded WWEIA meals via NutriBench (good for US/global, 11 countries) > Nutrition5k (photos, US cafeteria food) > LLM-labeled data (never as ground truth). Keep alias/portion tables tuned on a dev split and report on a frozen held-out split to avoid the overfitting trap noted in STEADY's own eval memory.
- Include adversarial/edge inputs: Hinglish code-switching, regional names, quantities as words ("do roti"), mixed units, brand names, and "no quantity given" defaults.

### Gaps
- No public weighed-food dataset for Indian home meals with text/voice descriptions was found; STEADY likely needs to build one.
- Nutrition5k primary error tables and nutritionist baseline numbers were not verified.
- No standard ±10% kcal tolerance benchmark across current models exists (NutriBench uses ±7.5 g carbs).

## 7. Model choice as of Nov 2026: accuracy, latency, cost for structured food parsing

### Takeaway

### Inferences
- **Cost math (parse call, text/voice):** ~1,500 input tokens (static prompt + few-shot + top-k candidates) + ~150 output tokens. Haiku 5.5: 1,500×$0.10/M + 150×$0.50/M ≈ $0.00023/log; gpt-6-luna ≈ $0.00023; gpt-4o-mini ≈ $0.00032; gpt-5.4-mini ≈ $0.0018. At 10 logs/day (300/month): $0.07–$0.54/user/month. Conclusion: optimize for accuracy/latency; the budget leaves room for a larger model on photos or for 3-sample self-consistency on low-confidence items only.
- **Where model quality actually matters after the architectural fixes:** food identification and unit/count extraction from messy multilingual speech — not calorie arithmetic (moved to DB). This is a classification/extraction task where small current models are likely adequate, but this must be verified on STEADY's held-out set (food-id accuracy, unit accuracy, p50/p90 latency, run-to-run identical rate).
- gpt-4o-mini is now an older, comparatively expensive-per-quality option next to gpt-6-luna and gpt-5-nano at similar or lower price — worth testing a swap, but only with the eval in place.
- Model-provider churn is high (Gemini 2.5 deprecations effective 2026-12-01, Anthropic removing sampling params): pin model IDs, include model ID in the cache key/`parser_version`, and re-run the eval on every model change.
